# 전체 활성 작업 수와 최근 작업 목록

2026-09-08. 개발 범위: 개선 목록 06. 운영 반영은 별도다.

최근 20개를 필터링한 숫자는 전체 활성 작업 수가 아니다. 공통 SQL 읽기 모델에서
work, workflow, control command, GJC 기록을 작업 ID로 묶고, 전체 활성 개수와
최근 목록을 같은 SQLite 읽기 트랜잭션에서 조회한다. 화면은 서버의 집계 값을 사용한다.

작업 상태는 work → workflow → command → GJC 순서로 선택한다. 같은 우선순위에서는
진행 중인 기록을 우선하고 시각·source ID로 순서를 고정한다. GJC 전송 완료는 연결된
업무의 완료 근거가 아니다. 최근 정렬 시각은 연결된 기록들의 가장 최근 시각이다.
workflow input.task_id/work_id, command target/args의 작업 ID와 run ID,
GJC continuation acceptance의 work ID를 정규화한다. project ID만으로 작업들을 합치지 않는다.
작업 정본 ID를 먼저 보존하고 단일 대상으로 해석되는 run/correlation/continuation 별칭을
source 정규화·상세 조회·숨김에 공통 적용한다. 여러 작업을 가리키는 correlation은
임의의 작업으로 병합하지 않는다.

숨김·격리는 대표 행 선정 이후의 페이지를 줄이는 필터가 아니다. 전체 연결 source/alias와
작업 ID를 검사해 하나라도 숨겨졌으면 그 작업 전체를 제외한 뒤 개수와 LIMIT를 적용한다.
목록·상세·집계는 같은 작업 정규화와 숨김 기준을 사용한다. 상세의 기존 그래프 기반
GJC 질문·프로젝트 승인 표시는 보존한다. 목록 pending_approval는 직접 연결된 상태 요약이다.

추천은 기존 canonical identity와 모든 전이 증거 검증을 유지한다. SQL로 가시성을 한 번
필터링하고 검증된 추천을 순회해 개수를 더한다. 최근 결과 배열은 요청한 개수까지만 유지한다.
같은 ID의 기본 작업과 추천은 추천 한 건으로 계산한다. 추천의 일부 순위만 종료됐으면
남은 활성 순위의 상태를 표시하고, 모든 순위가 종료됐을 때 활성 수에서 제외한다.
expired/superseded는 종료 상태다. 조회 시각만으로 원장에 없는 만료 전이를 생성하지 않는다.

대규모 추천 원장의 전체 증거 검증 비용과 상세 source_ids의 크기는 남는 비용이다.
정확한 집계를 위해 기본 작업 전체를 JS payload로 가져오는 방식은 사용하지 않는다.
추후 검증된 증분 집계를 도입할 때는 정정·삭제·복원과 원장 변조 검사를 함께 보존해야 한다.

검증: 신규 회귀 9개, 관련 백엔드 중복 제외 9파일43개, dashboard 29파일162개 통과.
실제 빌드 HTTP→Chromium에서 활성 21/최근20, 활성 한 건 숨김 후 20/20,
조회 DB 쓰기0과 page error0을 확인했다. 격리 합성 10,046행의 전체 집계+최근20
5회 측정 중앙값은 102.923ms다. 운영 트래픽이나 추천 대량 원장의 성능 수치가 아니다.
상세 증거와 잔여 전체 gate 상태는 개발 원장을 따른다.
